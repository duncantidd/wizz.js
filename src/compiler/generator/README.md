# Wizz Generator

## TL;DR

This directory is the final build-time stage of the Wizz compiler. It turns the analyzed component payload into one ES module that creates DOM nodes, mounts them into a target, performs initial reactive rendering, and exposes a `destroy()` method.

The generator expects parser and analyzer work to be complete:

```text
component source
  -> parser
  -> dependency analyzer
  -> node ID assigner
  -> generator
  -> ES module source string
```

`generateComponent()` in `componentGenerator.js` is the public entry point. It composes the other generator modules:

```text
analyzed payload
  -> findReactiveMutations(rawScript, prop names)   read-only prop enforcement
  -> interceptAssignments(rawScript, reactive names)
  -> generateCreateFunction(template)
  -> collectComponentRefNames(template, imports)
  -> generateUpdateFunction(template)
  -> CodeBuilder
  -> export default function mountComponent(target, props = {}) { ... }
```

The output is JavaScript source, not an immediately mounted component. The caller is responsible for bundling or evaluating the emitted ES module and calling its default `mountComponent(target, props)` export in a browser-like environment.

## Input Requirements

The generator consumes the payload produced by this sequence:

```js
const { parseComponent } = require('../parser');
const { analyzeDependencies } = require('../analyzer/dependencyAnalyzer');
const { assignNodeIds } = require('../analyzer/idAssigner');
const { generateComponent } = require('./componentGenerator');

const payload = assignNodeIds(analyzeDependencies(parseComponent(source)));
const moduleSource = generateComponent(payload);
```

The relevant payload fields are:

| Field | Producer | Generator use |
| --- | --- | --- |
| `rawScript` | Parser | Scanned for supported reactive mutations, then inserted into the component factory as developer logic. |
| `script` | Parser | Finds reactive declarations for context getters and initial change flags. |
| `template` | Parser | Drives DOM creation. |
| `Expression.value` | Parser | Becomes the JavaScript expression evaluated during updates. |
| `Expression.dependencies` | Dependency analyzer | Determines which `__wizzChanged` flags should trigger each expression update. |
| `data-wizz-id` attributes | ID assigner | Lets the hydration walk verify delivered elements. Updates never look nodes up by id. |

Calling `generateComponent()` without the analyzer stages can still produce source, but dynamic expressions will not have the metadata required for targeted updates. In particular, `generateUpdateFunction()` reads `dependencies` to decide which writes to emit.

## Generated Module Contract

Every generated module begins with a version header stamped from `../version.js`, so compiled artifacts self-identify the compiler and contract versions that produced them:

```js
// Generated by Wizz 1.6.0 (component syntax 1.2.0, generated output 1.6.0). Edits will be overwritten.
```

For a component with `let count = 0;` and `<p>Count: {count}</p>`, the result follows this shape:

```js
// Generated by Wizz ... Edits will be overwritten.

export default function mountComponent(target, props = {}) {
  // Developer logic is emitted here.
  let count = 0;

  const __wizzCtx = {
    get count() { return count; },
  };

  function __wizzCreate(__wizzCtx) {
    // Create elements and text nodes, then return the root element.
  }

  function __wizzUpdate(__wizzCtx, __wizzChanged) {
    // Update dynamic text when __wizzChanged.count is true.
  }

  const __wizzRoot = __wizzCreate(__wizzCtx);
  target.appendChild(__wizzRoot);
  __wizzUpdate(__wizzCtx, { count: true });

  return {
    destroy() {
      target.removeChild(__wizzRoot);
    }
  };
}
```

The original script and generated `create()`/`update()` functions share the `mountComponent()` lexical scope. This is why a generated update assignment can evaluate the raw expression text, such as `count + 1`, against the component's current local state.

## Server Rendering and Hydration

Two additional emission paths reuse the same pipeline. Both are gated by `assertServerRenderable()` in `serverGenerator.js`. The gate is "is the whole tree statically renderable": `{#if}`, `{#each}`, and imported component tags are renderable (each bodies keep the browser target's restrictions — one root element, no components, no `on:`); void elements with children, malformed `on:` directives, and reactive names matching `__proto__` or the reserved `__wizz` prefix are rejected with located diagnostics. A component tag requires `options.componentServerRenderable[name] === true` — vouched by the child's own eligibility at build level; a missing entry conservatively rejects, and `options.componentIneligibilityReasons[name]` chains the child's own failure into the diagnostic.

**Server target — `serverGenerator.js`:** `generateServerComponent(astPayload, options)` emits a module with no DOM dependency. It exports `renderComponent(props = {})`, which executes the author's top-level script verbatim (no assignment interception — there is no reactive update loop server-side), walks the template AST, and returns `{ html, state }` where `html` is the rendered string and `state` snapshots the reactive non-prop bindings. When the component (or any rendered child) declares `<wizz:head>`, the signature is `renderComponent(props = {}, options = {})` and the return gains the additive `head` field: the component's own head markup followed by each rendered child's head in tree order, every node carrying `data-wizz-head-id="<ownerPath>"` (page `'r'`, child `'r/<componentId>'` threaded through `options.headOwner`) and `data-wizz-loc` (file-qualified when the compile carries `filePath`). Head title text evaluates like body text (static and dynamic segments coalesce — titles are RCDATA, so no `<!-- -->` markers) and dynamic attributes use the same escaping; `on:` directives are skipped. Head emission is gated on static presence (`hasHeadMarkup` — own head, any style block, or any rendered component tag), so head-free style-free component-free pages keep the exact `{ html, state }` shape and byte-identical output. Child `.server.js` import specifiers optionally carry a `moduleQuery` option (a validated `?…` URL query) so a development server's in-process module cache re-evaluates the whole child graph after a rebuild — queries never propagate through static imports, so an undecorated cached child would keep serving stale markup and styles until restart. Production builds omit the option and emit clean specifiers.

With `options.extractedStyles` a linked stylesheet delivers the CSS: all three targets (client, hydratable, server) emit no style code, the scope attributes stay in the markup, and a style-only component compiles with no head machinery. The flag must match across a page's modules, because server delivery and hydration adoption share the style run. Without it, styled components additionally inject one deduped `<style data-wizz-style="<scope>" data-wizz-loc="…">` per document: the target threads a `__wizzStyleScopes` accumulator (page-created, shared with rendered children through the options argument) so a component imported by several pages or rendered twice injects exactly once. Style tags deliberately carry **no** `data-wizz-head-id` delivery tag — runtime scope dedup makes compile-time slice expectations impossible — and their CSS is raw-text escaped (`<` → `\3c `) so a rule can never terminate the tag early. It also exports `serializeInitialState(state)` producing `<script type="application/wizz-state">…</script>` with every `<` escaped; the script must be delivered as a sibling of the mount point. Emission rules that keep browser parsing aligned with the template AST:

- Text escapes `&`, `<`, `>`; attribute values additionally escape `"` (with `&` escaped first). Expression output goes through the same escaping.
- Adjacent text-like children (Text/Expression) are separated by `<!-- -->` markers; when an element's direct children include a block, markers are also emitted at branch boundaries. Wizz templates cannot contain comments, so the marker is unambiguous, and browsers otherwise merge adjacent text nodes and break positional targeting. Over-marking is harmless — the hydration walk strips comments.
- Elements never emit self-closing syntax; void elements (`area base br col embed hr img input link meta param source track wbr`) get no end tag and must have no children. Every other element closes even when it has no children — an unterminated start tag stays open in the browser and swallows the following markup into it, breaking the delivered childNodes' one-to-one alignment with the template positions the hydration walk verifies.
- `on:` attributes are skipped (client-only); `data-wizz-id` flows through for hydration.
- Dynamic attributes are serialized by `serverAttributeSource()`, the server half of `attributePolicy.js`: every `BOOLEAN_ATTRIBUTES` name (including `checked` and `disabled`) renders bare when truthy and is omitted when falsy; any other name (including `value`) is omitted for `null`/`undefined` and otherwise rendered as `name="escapeAttribute(value)"`. Each expression is evaluated once.
- `{#if}` evaluates the test against render-time state and emits the taken branch between block markers; `{#each}` loops the initial collection with the item variable in scope; component tags namespace-import the child's `.server.js` build (`import * as __wizzServer_<Name> from "./<Name>.server.js"`) and embed its `renderComponent()` output at the tag position, collecting child state under `state.__wizz.components["<componentId>"]`.

**Hydration — `hydrationGenerator.js`:** `generateHydrationFunction(templateAST)` emits a `__wizzHydrateCreate(target, state, adoptSelf)` function that `componentGenerator.js` embeds when `generateComponent(astPayload, { hydratable: true })` is requested. Hydratable modules export `hydrateComponent(target, props, state)` (adopting the mount point's first element child) and `hydrateRoot(__wizzRoot, props, state)` (adopting the *given* node — the nested-adoption entry); all entries route through a shared `__wizzMountInstance()` closure that seeds reactive non-prop bindings from the serialized state (`Object.prototype.hasOwnProperty.call` + bracket access, so a hostile `__proto__` key cannot pollute; props are never seeded) and adopts the server root instead of creating one. The adoption walk verifies positionally against the AST:

- The mount point's `firstElementChild` (or the given node, when self-adopting) becomes the root; its lowercased tag must match the template.
- Each element's comments (the delivery markers) are stripped first, then the remaining `childNodes.length` must equal the flattened AST child count exactly.
- Text children verify `nodeType === 3` and their `nodeValue` against the escaped-decoded literal; expression children verify against `String(<raw expression>)` evaluated in the seeded factory scope.
- `{#if}` re-evaluates the same test the server evaluated against seeded state and walks only the taken branch; `{#each}` adopts each item root positionally, rebuilds the records map with key-aware update closures (so client list updates mutate the adopted nodes), and creates only the list anchor — an empty text node cannot survive HTML serialization.
- Imported component tags verify only that the position holds an element; the child is adopted after the walk passes through the child's own `hydrateRoot(childNode, props, state)` with the state slice under `__wizz.components`. Component-tag walk refs are declared at `__wizzHydrateCreate` scope so tags inside branches stay addressable.
- `data-wizz-id` values are read from the AST attribute, never from a walk counter.
- Event listeners are collected during the walk and attached only after it passes.
- When the component (or a rendered child) declares `<wizz:head>`, `__wizzHydrateCreate(target, state, adoptSelf, headOwner)` also adopts the delivered head: the page filters the marker-delimited run (`<!--wizz:head-start-->…<!--wizz:head-end-->` injected by the dev server before `</head>`) to nodes tagged with its owner path (`'r'`), nested children scan `document.head` for their `'r/<componentId>'` slice (the parent's claim removes delivery tags first, so the filters cannot collide). Verification compares each node against compile-time expectation structures `{ tag, text, attrs: [[name, value]], flags: [[name, ''|null]] }` — pair arrays, not attribute objects, so a hostile key cannot pollute prototypes and no DOM is created. Success claims the slice (`__wizzClaimHead`: ownership re-tagged `data-wizz-head`, delivery tags consumed, claimed titles moved to the head front — the position `document.title` reads), consumes the markers, and returns `headNodes` for destroy-time release. Any mismatch — wrong tag, text, attribute, boolean presence, count, or unclaimed leftover delivery tags — joins the same single-warning fallback: claimed head nodes released, the delivered run (or, for a nested adoption, the component's own slice via `__wizzStripOwnedHeadSlice`) stripped, then a fresh head applied. Scoped styles ride the same adoption path without slice claims: because style tags carry no delivery tag, the leftover-run check ignores them, and the hydrate path re-applies its stylesheet through `__wizzApplyHead`, which finds the delivered copy by scope and refcounts it — server-delivered styles are adopted, never duplicated, and a fallback's fresh mount adopts the delivered copy too.

Any mismatch produces exactly one `console.warn('[wizz] hydration mismatch: … Falling back to client rendering.')`, clears the mount point, and returns `null`; the factory then falls back to a full client `mountComponent()` call. For a nested adoption (`hydrateRoot`), the fallback clears and remounts **inside the given node**, so the parent tree is never detached and never fails. Dynamic attributes other than `data-wizz-id` are not verified — the initial `update()` pass converges them from the seeded state. Known boundary: CRLF-authored templates fail strict text verification and fall back rather than hydrating.

`__wizzCtx` currently exposes getter access to each reactive declaration and is passed to both lifecycle functions. It establishes the framework context boundary and ensures a getter reads the current local binding; the present generated expression code evaluates directly in the factory closure rather than reading through `__wizzCtx`.

## Component Props

Props let a parent pass explicit inputs to an imported child component without ambient state.

**Declaration (child):** `export let name = 'Guest';` declares a prop with a default; `export let count;` declares one whose default is `undefined`. Only `export let` is prop syntax, one declarator per statement, terminated with a semicolon. Prop names cannot be reserved words, `props`, `__proto__`, or use the reserved `__wizz` prefix. The parser removes the statements and the generator emits the bindings ahead of the developer logic, so props are reactive variables exactly like `let` state: template expressions and dynamic attributes depending on them rerender when the value changes.

```js
let name = props.name !== undefined ? props.name : ('Guest');
let count = props.count;
```

**Passing (parent):** every attribute on an imported component tag is a prop. Component tags create no DOM element, so native attribute semantics never apply to them: static attributes pass their string, bare attributes pass `true`, and dynamic attributes pass the evaluated expression. `on:*` directives and children on component tags are compile errors. Attributes the child never declared are ignored — the build compiles files independently, so cross-file validation happens through the child's consumption, not the parent's compilation.

**Mounting:** the child factory receives the props object explicitly as its second argument — `Counter(parent, { "start": count })` — never through shared or ambient scope.

**Read-only:** prop bindings are read-only inside the child. Any statement-level mutation of a prop name (`name = x`, `name++`, `name += x`, `name.prop = x`) is a compile-time error located in the source. Shadowing is respected: a function parameter or block-scoped `let`/`const`/`var` with the same name is a local, not the prop. Mutations in expression position remain outside the scanner's documented boundary, as for reactive state.

**Reactive updates:** the parent's `update()` delivers changes through the child instance:

```js
if (__wizzChanged.start) {
  if (component_1) component_1.setProps({ "start": start });
}
```

Each tag with reactive props gets a factory-scope reference (`component_<componentId>`, assigned at mount by the generated `create()`), so updates never remount the child and its identity is stable across parent rerenders. `setProps(next)` skips destroyed children, ignores keys the child did not declare, compares values with `Object.is` so identical updates are free, and re-applies the declared default when the parent explicitly passes `undefined` — the same "not provided" contract as mount time. Delivered changes flow through the child's own batched scheduler, so one parent update produces at most one child rerender.

**Component identity in lists:** imported components are not supported inside each blocks (compile-time error, unchanged). Identity semantics are therefore defined for directly nested components only; keyed per-item component reconciliation is future work.

## Files

### `codeBuilder.js` - Source Formatting Utility

**Export:** `CodeBuilder`

`CodeBuilder` is the small shared utility that produces readable, deterministic generated code. It stores output as lines and applies two spaces per indentation level when adding each line.

#### `new CodeBuilder()`

The constructor initializes an empty `lines` array and `indentLevel` of zero. A fresh builder generates an empty string until code is added.

#### `add(code)`

Adds one string line at the current indentation level and returns `this`, enabling fluent emission:

```js
builder.add('function __wizzCreate() {')
  .indent()
  .add('return __wizzNode_1;')
  .dedent()
  .add('}');
```

It throws `TypeError` for non-string input. Keeping this validation at the formatting boundary catches generator mistakes before an invalid value is quietly converted into code text.

#### `indent()` and `dedent()`

`indent()` increases indentation for subsequent lines. `dedent()` decreases it only when above zero, so an unmatched call cannot produce negative indentation. Both return `this` for chaining.

#### `generate()`

Joins accumulated lines with `\n` and returns the final source string. It does not append a trailing newline, which makes output stable for string-based tests and embedding in larger generated modules.

### `domGenerator.js` - DOM Creation Emitter

**Exports:** `generateCreateFunction(templateAST, componentImports)`, `collectComponentRefNames(templateAST, componentImports)`

`generateCreateFunction()` emits a `function __wizzCreate(__wizzCtx) { ... }` declaration that builds the static structure of the component using native DOM APIs. It does not mount the result; it returns the constructed root node to the component wrapper. `collectComponentRefNames()` is the component-generator helper that lists the factory-scope reference names for tags with reactive props.

#### Root Selection

Components currently require a top-level `Element` node. The generator uses the first such child under `templateAST.children` and ignores surrounding root-level text, which allows formatting whitespace outside the component element. It throws:

```text
Component template must contain a root element.
```

when no top-level element exists.

#### `walk(node, parentVarName)`

The nested walker emits one local variable per AST node, named sequentially as `__wizzNode_1`, `__wizzNode_2`, and so on. It stores the correspondence in `nodeVariables`, which is maintained as generation-time bookkeeping for AST-to-variable associations.

For each supported node type, it emits:

| AST node | Generated DOM operation |
| --- | --- |
| `Element` | `document.createElement(name)` plus attribute assignment |
| Imported component tag | Holds its position with an empty text node, then mounts the component before that node and removes it |
| `Text` | `document.createTextNode(value)` |
| `Expression` | `document.createTextNode(String(expression))` |

Every generated child is appended to `parentVarName` immediately after creation, and the recursive traversal then creates descendants in source order.

Component tags mount later, through `__wizzMountChildren()`, because a child's head must apply after its parent's and its `onMount` hooks need the tree attached. To keep template order, `create()` appends an empty text node at the tag's position and passes it as the child's third mount argument. The child inserts its root before that node, and the parent removes the node straight after, so a fresh mount produces the same DOM hydration adopts.

For attributes, a normal value produces `setAttribute(name, value)`. A parser-produced boolean attribute has `value: null` and produces `setAttribute(name, "")`, matching HTML's presence-based boolean attribute representation. Dynamic values such as `value={name}` are evaluated during creation and on every change to their reactive dependencies. `value`, `checked`, and `disabled` are assigned as DOM properties; other dynamic names go through the module-level `__wizzAttr(node, name, value, boolean)` helper defined in `attributePolicy.js`. For HTML boolean attributes (`hidden`, `required`, `open`, `inert`, ...; the list is `BOOLEAN_ATTRIBUTES`) the call passes `1` and the attribute is set to `""` when the value is truthy and removed when falsy. Every other name is removed for `null`/`undefined` and otherwise set to `String(value)`; `false` intentionally renders `"false"` because enumerated attributes such as `aria-*` and `draggable` give it meaning. The helper is emitted only when a native body or head element carries a dynamic attribute it writes, and uses only `setAttribute`/`removeAttribute`, never markup injection. Head nodes use the same helper for every dynamic name (no property path), the server target applies the same policy when serializing (`serverAttributeSource()` in `serverGenerator.js`), and hydration's head verification expects a removed attribute to be absent. An explicit event directive such as `on:click={handleClick}` emits `__wizzListen(node, "click", handleClick)` instead of an inline attribute, so the listener retains access to the component factory's local state and functions. Event directive values may be any non-empty JavaScript listener expression, including an arrow function that receives the native event: `on:click={(event) => increment(event.detail)}`. The generator embeds this expression as the listener. The one transform is mutation interception: the component generator runs each handler through `interceptHandlerExpression()` (see `assignmentInterceptor.js`) and passes the results in as `handlerSources`, a `WeakMap` keyed by attribute object; an attribute without an entry emits its raw value. `__wizzListen()` is a factory-scope helper that calls `addEventListener()` and records the node, event name, and handler in a `__wizzListeners` registry so `destroy()` can remove every listener the framework attached.

Names, text content, and attribute values are embedded with `JSON.stringify()`. That is important for correct generated JavaScript when source contains quotes, backslashes, or newlines; they are emitted as valid string literals rather than interpolated unsafely into source code.

An imported component is recognized only when its tag name matches a default `.wizz` import from the component script, for example `import Counter from './Counter.wizz';` with `<Counter />`. The generated module moves this import to module scope and changes the specifier to `./Counter.js`. Component tags must be nested in a native element and have no children; their attributes become the props object passed to the child's factory (static values as strings, bare attributes as `true`, dynamic values as the expression). Event directives and a `__proto__` attribute are compile errors on component tags. A tag with reactive prop attributes also assigns the mounted instance to its factory-scope reference `component_<componentId>` so the update function can deliver prop changes; tags without reactive props mount inline. Mount results are retained so the parent component's `destroy()` can destroy each child before removing the parent root.

Each blocks compile into a collection reconciler. Given `{#each items as item (item.id)}<li>{item.name}</li>{/each}`, it keeps a record for every key, reuses and moves the record's root node when its key remains present, updates its repeated text and dynamic attributes with the new item value, creates records for new keys, and removes records for deleted keys. Duplicate keys throw at runtime.

The keyless form `{#each items as item}` reconciles positionally: the record key is the array index, so on reassignment each record updates in place with the item now at its position, records are created at the end as the collection grows, and records beyond the new length are removed. DOM nodes are reused by position rather than by item identity, which is the predictable choice for primitive collections such as `['item1', 'item2']`.

Both forms share two structural rules. Each block must be nested inside a native element, because the reconciler inserts its records before an anchor text node in that parent. Formatting whitespace around the body is ignored, but the body must contain exactly one native root element — the generated record tracks a single root node so it can be moved and removed during reconciliation, and only an element root gets generated text and dynamic-attribute updates — and imported components are not supported in the body yet. Violating the single-root rule is a compile-time error rather than silently rendering only the first root. Event directives and nested `if` or `each` blocks inside a body are also compile-time errors rather than silently dropped nodes; per-item listeners are deferred until handler-context machinery exists, because an inline handler would otherwise close over the item value present when its record was created and fire stale after updates.

Expressions create text nodes from `String(expression)` during initial DOM construction. This renders both reactive `let` values and non-reactive `const` values at mount time. `componentGenerator.js` still invokes `update()` once during mount so the reactive update path is exercised consistently.

### `updateGenerator.js` - Reactive Text Update Emitter

**Export:** `generateUpdateFunction(templateAST)`

`generateUpdateFunction()` emits `function __wizzUpdate(__wizzCtx, __wizzChanged) { ... }`. The generated function walks no AST at runtime. Instead, this generator walks the analyzed AST at build time and writes direct DOM operations for every known reactive interpolation.

#### `walk(node)`

The nested walker starts at the root element `create()` renders and handles `Element`, `Expression`, and `IfBlock` nodes (a branch taken at mount stays in the DOM, so its reactive content participates in updates). Imported component tags are recognized by their analyzer-assigned `componentId` and take a separate path: each reactive prop attribute emits one guarded `setProps()` call instead of a DOM attribute write.

#### `collectUpdateTargets(templateAST)`

Every node `update()` writes to, meaning an element with a reactive attribute or a reactive expression, gets a factory-scope variable named `__wizzTarget_N`. `create()` assigns it from the node it builds, the hydration walk assigns it from the node it adopts, and `update()` reads it:

```js
let __wizzTarget_1;

function __wizzCreate(__wizzCtx) {
  // ...
  const __wizzNode_5 = document.createTextNode(String(count + 1));
  __wizzTarget_1 = __wizzNode_5;
  // ...
}

function __wizzUpdate(__wizzCtx, __wizzChanged) {
  if (__wizzChanged.count) {
    __wizzTarget_1.nodeValue = String(count + 1);
  }
}
```

Each generated block checks one property of `__wizzChanged` and writes `String(expression)` to the captured node. An expression with several dependencies gets a block for each one, so a change to any referenced variable recalculates the whole expression.

Writes never look a node up, because neither lookup is reliable at runtime. `data-wizz-id` values restart at `1` in every component, so a subtree query can match an element inside a child component. A template child index stops matching the DOM beside child components (which mount after their siblings), untaken branches, and list items.

Nodes inside `{#if}` are returned in `conditional`, and their writes carry an `if (__wizzTarget_N)` guard because an untaken branch never assigns the variable. The guard is emitted only there, so other writes stay unconditional. A future reactive `{#if}` must clear these variables when it tears a branch down.

Each bodies are not targets: list records hold and update their own nodes. The variables keep no extra memory alive after `destroy()`, because the closure's `__wizzRoot` already references the same subtree.

Templates with no reactive content generate an empty `update()` body and declare no target variables.

### `attributePolicy.js` - Dynamic Attribute Policy

**Exports:** `PROPERTY_ATTRIBUTES`, `BOOLEAN_ATTRIBUTES`, `isBooleanAttribute(name)`, `attributeWriteSource(nodeRef, name, valueSource, { properties })`, `attributeValueSource(name, valueSource)`, `needsAttributeHelper(root, { properties, componentNames })`, `__wizzAttr`

The single policy for how a dynamic attribute reaches the DOM, shared by `domGenerator.js`, `updateGenerator.js`, `hydrationGenerator.js`, `componentGenerator.js` (head nodes), and `serverGenerator.js`:

- `value`, `checked`, and `disabled` on body elements are assigned as DOM properties. The match is case-insensitive and always assigns the lowercase property, so `DISABLED={x}` emits `.disabled = x`. Head nodes pass `properties: false` and use attributes for every name.
- Names in `BOOLEAN_ATTRIBUTES` (the HTML boolean attributes, matched case-insensitively at compile time) emit `__wizzAttr(node, name, expr, 1)`: present as `""` when truthy, removed when falsy.
- Every other name emits `__wizzAttr(node, name, expr)`: removed for `null`/`undefined`, otherwise `String(value)`. `false` deliberately renders `"false"` because enumerated attributes (`aria-*`, `draggable`, `spellcheck`) give it meaning.

`__wizzAttr` is emitted once at module scope via `Function.prototype.toString()`, only when `needsAttributeHelper()` finds a native element with a helper-written dynamic attribute, so other modules stay byte-identical. It uses only `setAttribute`/`removeAttribute`. Attribute names are always emitted as JSON string literals. `attributeValueSource()` gives hydration's head check the expected serialized value, or `null` for an absent attribute.

### `reservedNames.js` - Author Name Check

Author scripts run inside the generated factory, and author expressions run inside its nested functions. Every name the generators declare there, in the client, hydratable, and server targets, therefore carries the reserved `__wizz` prefix, so an author variable can neither collide with one (a module that fails to load) nor be shadowed by one (a wrong value at runtime). Any new generated local must use the prefix too.

A few names cannot be renamed. `assertAuthorNames()` rejects them with `WIZZ-G025` when declared at the top level of a script, or used as a prop or import name: the `__wizz` prefix, `onMount`, `onDestroy`, and the globals generated code reads inside the factory. Imports are also checked against the module's own exports. Declarations are read from script tokens, so a name inside a function or block stays allowed. If generated factory code starts reading another global, add it to `FACTORY_GLOBALS`.

### `serverGenerator.js` - HTML String Renderer Emitter

**Exports:** `generateServerComponent(astPayload, options)`, `assertServerRenderable(astPayload, options)`, `VOID_ELEMENTS`

`generateServerComponent()` emits a DOM-free server module exporting `renderComponent(props = {})` and `serializeInitialState(state)`; rendered component tags add `__wizzServer_<Name>` namespace imports of the children's server builds. The escaping helpers are emitted into each module via `Function.prototype.toString()`, so the output stays import-free apart from child server modules. `assertServerRenderable()` is the shared static-renderability gate used by both the server target and hydratable generation; its errors carry the template location of the offending construct and chain child failures through `componentIneligibilityReasons`. See [Server Rendering and Hydration](#server-rendering-and-hydration) for the emission rules and delivery boundaries.

### `hydrationGenerator.js` - Adoption Walk Emitter

**Export:** `generateHydrationFunction(templateAST)`

`generateHydrationFunction(templateAST, componentImports, headBlock, options)` emits the `__wizzHydrateCreate(target, state, adoptSelf, headOwner)` function and its local helpers (`__wizzNodeTag`, `__wizzStripComments`, `__wizzDescribe`, plus the per-list adoption machinery and `__wizzReadSlice` when the template renders components). The walk mirrors `create()`'s pre-order over the flattened if/each sequence and verifies each position against the template AST, deferring event listeners until the walk passes and funneling every mismatch through one `console.warn` before clearing the mount point and returning `null`. It is embedded by `componentGenerator.js` only when `hydratable: true` is requested; the walk closes over the factory scope so expression verification re-evaluates the author's own expressions against seeded state.

### `../scriptLexer.js` - Script Tokenizer (compiler-root utility)

**Exports:** `tokenizeScript(source)`, `matchTemplateTokens(tokens)`

`scriptLexer.js` lives at the compiler root rather than in this directory because two stages consume it: the assignment interceptor below and the parser's prop extractor. It is a shared lexical utility, not a pipeline stage.

`tokenizeScript()` turns raw component script into a flat token stream. Each token records its `type` (`identifier`, `number`, `string`, `regex`, `templateText`, `comment`, or `punctuator`), its `value`, and its original `start`/`end` offsets so consumers can splice the source text without regenerating it. Comments are emitted as tokens to keep offsets aligned. Template literals emit their text as opaque `templateText` tokens and tokenize the code between `${` and `}` normally, tagging the closing `}` with `interpolationClose: true` so nesting stays unambiguous.

The one lexical ambiguity the lexer resolves is `/`: it starts a regular expression literal unless the previous significant token ends an operand (identifier outside a regex-allowing keyword, number, string, template text, another regex, or `)`/`]`/`}`/`++`/`--`), in which case it is division. This matches the heuristic real engines use at the lexical level. Unterminated strings, templates, comments, and regexes degrade gracefully (the slash falls back to a division punctuator) so scanning always progresses and never hangs.

`matchTemplateTokens()` pairs opening and closing backticks across nested interpolations so consumers can skip a whole template in one step.

### `assignmentInterceptor.js` - Reactive Mutation Rewriter

**Exports:** `interceptAssignments(rawScript, reactiveVars, persistentVars)`, `findReactiveMutations(rawScript, names)`, `interceptHandlerExpression(expression, reactiveVars, persistentVars)`, `findHandlerMutations(expression, names)`, `normalizeHandlerExpression(expression)`

`interceptAssignments()` preserves the component's script source while adding a `__wizzQueueUpdate({ name: true })` call after each supported mutation of a reactive variable. The optional third argument lists persistent variables as `{ name, storageKey }` pairs: mutations of those names additionally emit `__wizzPersistWrite("key", name)` after the notification, so the new value reaches storage and every subscribed mount. For example:

```js
count += 1;
// becomes
count += 1; __wizzQueueUpdate({ count: true });
```

It is syntax-aware: `scriptLexer.js` tokenizes the script, and rewrites are decided on the token stream with a context stack. A mutation is rewritten when it begins a statement inside the component top level, a block, a function or arrow body, or a switch body — including arrow-function callbacks such as `onMount(() => { count = 1 })` that older compiler versions left untouched. Function and arrow parameters shadow component state, so mutations of parameter names inside their own body (`items.map(count => { count = 1; })`) are left alone. Block-scoped `let`, `const`, and `var` declarations shadow the same way: a mutation of a locally declared name never notifies the dispatcher, while component-scope declarations are the reactive state itself. For-loop header declarations shadow the braced body that follows. Statements that omit semicolons are handled through automatic semicolon insertion: the statement ends at a newline after a completed operand, and the notification is inserted with a leading `;` when needed.

`findReactiveMutations()` runs the same scanner without rewriting and reports every detected mutation with its source line and column. The component generator uses it to enforce read-only props: any detected mutation of a prop name is a compile-time error.

Assignments are not rewritten in expression position: inside parentheses that are not function bodies (`if (count = 1)`, call arguments), inside object literals and class field initializers, inside template `${}` interpolations, in unbraced `if`/`else`/`while`/`do` statement bodies, or as a chained assignment beyond the first target. Property chains such as `user.name = "Ada"` and `items[0] = "x"` rewrite with the root reactive name, matching how reactive objects are re-read on update. Supported mutations use `=`, the compound assignment family, and prefix or postfix `++`/`--`, and the original assignment text is preserved rather than reconstructed.

Whenever the extent of a statement cannot be established confidently (unbalanced nesting, an unpaired ternary `:`, an unpaired backtick), the surrounding source passes through untransformed. A missed interception is acceptable, corrupted output is not. The component wrapper provides `__wizzQueueUpdate()` before executing developer logic; it calls `update()` only after initial mounting completes, which makes initialization assignments safe because DOM creation reads their final values directly.

**Inline `on:` handlers.** `interceptHandlerExpression()` applies the same rewrite to a directive value. `normalizeHandlerExpression()` first accepts only a function literal that spans the whole value — `function (...) { ... }`, a block-bodied arrow, or an expression-bodied arrow (with optional `async`, a bare or parenthesized parameter list) — and rewrites an expression body into a block body, `(e) => name = e.target.value` becoming `(e) => { name = e.target.value }`, so the body is a statement the scanner can instrument. Dropping the expression body's value is unobservable because `addEventListener()` ignores listener return values. Everything else returns `null` and is emitted untouched: handler references and calls, a value that is itself an assignment (it would run at mount), a sequence whose first element is the arrow (`(e) => a = 1, b`, where a block would swallow `b`), a body beginning with `function`, `class`, or `let` (those become declarations as statements), and unbalanced heads. A trailing `//` comment moves the closing brace to a new line. Handlers without a statement-level reactive mutation come back byte-identical, so their generated output never changes. Parameters shadow reactive names as in the script. `findHandlerMutations()` is the read-only counterpart: the component generator uses it to reject inline mutations of props with `WIZZ-G015`.

### `persistInitializer.js` - Persistent Initializer Splicer

**Export:** `rewritePersistInitializers(rawScript, declarations, buildReplacement)`

`rewritePersistInitializers()` replaces each persistent declaration's recorded `persist(key, default)` span with a target-specific initializer, splicing back-to-front by offset so earlier replacements never shift later spans. `buildReplacement(declaration)` receives the declaration node (`storageKey`, `defaultValue`) and returns the replacement text: the client target builds `__wizzPersistRead("key", (default))`, the server target builds `(default)`. Scripts with no persistent declarations pass through byte-identical, `persist(...)` text in comments or strings is never touched (spans, not text matching), and a span that no longer starts with `persist` — compiler-internal drift — throws a located `SyntaxError` naming the bug rather than splicing garbage into author code.

### Persistent State

A `let name = persist(key, default)` declaration is an ordinary reactive variable with a storage key attached. The machinery is emitted only when at least one declaration is persistent — components without one are byte-identical apart from the version stamp — and the three runtime helpers are emitted per-module (like the head helpers, via `Function.prototype.toString`) while the bus they share is a `globalThis.__wizzStateBus` singleton, so one bus serves every module on the page.

- `__wizzPersistRead(key, fallback)` reads `localStorage` defensively: absent storage or a stored `null` yields the fallback, `JSON.parse` failure (corrupted or hostile entry) yields the fallback, and the stored value replaces the variable wholesale — never merged, which keeps hostile stored objects away from any merge vector.
- `__wizzPersistWrite(key, value)` is appended to every intercepted statement mutation of a persistent variable (after `__wizzQueueUpdate`, both the semicolon-terminated and automatic-semicolon forms). It writes `JSON.stringify(value)` through a guarded `setItem` (quota or private-mode failures leave the in-memory state intact), posts `{ key, value }` on the bus's BroadcastChannel when one exists, and delivers same-tab so instances sharing the key converge within the writing tab.
- `__wizzPersistSubscribe(key, callback)` registers the mount's callback in the bus's per-key registry and returns an unsubscribe; the mount pushes one subscription per persistent key and unregisters all of them in a destroy hook. The subscription callback applies the value with an `Object.is` guard — a component's own write does not echo back into it — then assigns and queues an update.

The bus opens one `BroadcastChannel('wizz-state')` per page for cross-tab delivery, with a `storage` event listener as the no-BroadcastChannel fallback (a tab's own storage event never fires for its own write, and a removed key leaves mounted state alone until the next mount reads storage). Node-style channels are `unref`ed so an idle bus never holds a process open. During hydration, persistent variables are seeded from the serialized snapshot like every other reactive var — the delivered markup was rendered from that state, and the adoption walk verifies by re-evaluating expressions, so the walk's checks match the delivery by construction (verifying against the storage-read value instead made every stored value that differed from the default fail the walk and fall back). The captured storage-read values are restored as soon as the walk returns — client storage stays the mounted truth — and because the emitted initial `update()` pass runs unconditionally after adoption, hydrated markup shows the stored value on the first pass with no extra sync machinery. Branch selection stays a mount-time choice (`create()`/`__wizzHydrateCreate()` pick the `{#if}` branch; `update()` carries no branch machinery), so an adopted branch whose test reads a persistent var keeps the delivered branch. Server modules rewrite the marker to `(default)` and emit no persistence machinery at all: the server has no storage, the default is what renders, and hydration hands the client initializer the real value.

### Update Scheduling

`__wizzQueueUpdate()` does not call `update()` synchronously. Each call merges its flags into a pending set (`{ ...pendingChanges, ...changed }`), and if no flush is scheduled it schedules exactly one `queueMicrotask` flush. The flush hands all merged flags to a single `update()` pass and clears the pending set. An event handler that assigns several reactive variables therefore produces one DOM update with one combined `__wizzChanged` object, not one update per assignment. Because the flush runs on a microtask, the DOM settles before the browser paints.

Scheduling is per component: the scheduler state (`__wizzBatched`, `__wizzPending`) lives in each factory closure. Calls before mounting completes return immediately, so initialization assignments never schedule; creation and the initial synchronous `update()` render their final values. `destroy()` sets `__wizzDestroyed`, and a flush that fires after destroy returns without calling `update()`, so a pending batch never touches a torn-down component.

### Lifecycle Hooks

The factory emits two registration functions that component scripts call directly, with no import: `onMount(hook)` pushes to `__wizzMountHooks` and `onDestroy(hook)` pushes to `__wizzDestroyHooks`. Both are function declarations hoisted above the developer logic, so registration works from any statement in the script.

Mount hooks run once at the end of initialization, after the root is attached to `target`, child-component mounting, the initial synchronous `update()`, and `__wizzMounted = true`. Because hooks run with `__wizzMounted` already set, an assignment inside a hook schedules a batched update that renders on the following microtask. Destroy hooks run at the start of `destroy()`, after `__wizzDestroyed = true` but before child components are destroyed, tracked listeners are removed, and the root node is removed, so cleanup code still sees the attached DOM; any state assignment a destroy hook makes schedules a batch whose flush is skipped by the `__wizzDestroyed` guard.

Hooks must be registered while the factory body executes (the script's top level or code it calls during setup); a registration after mounting or after destroy is pushed but never invoked. `onMount` and `onDestroy` are provided by the generated closure, so the assignment interceptor reports neither as a reactive variable and never touches the registration statements themselves. State mutations inside hook callbacks — including inline arrow bodies such as `onMount(() => { status = "ready"; })` — are intercepted at statement level and schedule batched updates like any other mutation.

### `componentGenerator.js` - Mountable ES Module Emitter

**Export:** `generateComponent(astPayload, options = {})`

`generateComponent()` is the public composition layer. It creates a `CodeBuilder`, emits the factory function, delegates DOM and update function bodies to their dedicated generators, then emits mounting and teardown code. With `options.hydratable: true` it first gates the payload through `assertServerRenderable()` and switches to a triple-export emission (`mountComponent`, `hydrateComponent`, `hydrateRoot`) routed through a shared `__wizzMountInstance()` closure (see [Server Rendering and Hydration](#server-rendering-and-hydration)); without the flag the emission is byte-identical to the single-argument call.

Its generated factory has these phases:

1. **Version header:** emits the self-identification comment from `../version.js` before any imports.
2. **Read-only prop check:** when the payload declares props, runs `findReactiveMutations()` over the script and throws a located `SyntaxError` for any statement-level mutation of a prop name.
3. **Factory signature:** emits `export default function mountComponent(target, props = {}, __wizzAnchor = null) {` (hydratable modules add the `hydrateComponent`/`hydrateRoot` exports and open the shared `__wizzMountInstance(target, props, __wizzAnchor, hydrate, state, adoptSelf)` closure instead).
4. **Developer logic:** emits the prop bindings (`let name = props.name !== undefined ? props.name : (default);` in declaration order), a guarded `__wizzQueueUpdate()` dispatcher, sends `rawScript` and reactive declaration names through `interceptAssignments()`, then writes the resulting source line by line into the factory closure. Recognized mutations update mounted components, while initialization-time mutations are safe because they run before `__wizzMounted` is set. Hydratable modules then seed non-prop reactive bindings from the verified state object.
5. **Framework context:** filters `astPayload.script` for reactive declarations and emits a getter for each name. Props are reactive declarations, so they get context getters too. `const` declarations and function declarations do not become context getters.
6. **DOM creation:** inserts the source from `generateCreateFunction(astPayload.template, componentImports, handlerSources)` (the instrumented inline handlers collected by `collectHandlerSources()`, which also rejects prop mutations in handlers), preceded by a `let component_<id> = null;` declaration for every imported component tag with reactive props — the factory-scope reference shared by `create()` (which assigns the instance at mount) and `update()` (which delivers prop changes). Hydratable modules insert `generateHydrationFunction()`'s adoption walk immediately after.
7. **Reactivity engine:** inserts the source from `generateUpdateFunction(astPayload.template)`, which routes reactive prop attributes to `component_<id>.setProps(...)` instead of DOM writes.
8. **Initialization:** calls `__wizzCreate(__wizzCtx)` (or adopts via `__wizzHydrateCreate(target, state, adoptSelf, headOwner)` on the hydrate path, falling back to a client mount on mismatch — nested adoptions fall back *inside* the given node), appends the returned root node to `target`, applies the component's head (fresh mounts build head nodes via `createHeadNodes()` and prepend them through `__wizzApplyHead`; hydrated mounts take the adopted `headNodes` from the adoption walk or apply fresh ones), mounts child components (hydrated children are adopted through the child's own `hydrateRoot`, threaded the owner path `'r/<componentId>'` on the head path), invokes `__wizzUpdate(__wizzCtx, __wizzChanged)` with every reactive variable set to `true`, then sets `__wizzMounted` to `true`. Creation renders every expression initially; this first update establishes the regular reactive update path before intercepted mutations can trigger it.
9. **Public API:** returns `{ setProps?, destroy() }`. `setProps(next)` exists only when the component declares props and applies parent-supplied values as described under "Component Props". `destroy()` marks the component destroyed — cancelling any pending scheduled update — runs destroy hooks, destroys mounted child components (releasing their adopted heads through the child cascade), releases the component's own head nodes via `__wizzReleaseHead`, removes every tracked event listener, and removes the root node from `target`.

A component's head machinery is emitted only under the `headActive` gate — the component declares its own `<wizz:head>` or `<wizz:style>`, or (for hydratable modules) it renders head-declaring children whose delivered slices must be attributable. Otherwise the module is byte-identical apart from the header stamp. When active, the module carries six flush-left helpers plus a module-level owner sequence:

- `__wizzApplyHead(nodes, loc)` — tags fresh head nodes `data-wizz-head="h<n>"` and prepends them to `document.head`; warns once when another owned `<title>` is already mounted, naming both locations. Prepending puts the freshly applied title at the head front — the position `document.title` reads — so the deepest component's title wins and releasing it lets the previous owner's resume. Style nodes (`<style data-wizz-style>`) dedup by scope instead: an existing copy — delivered server-side or applied by an earlier mount — has its `data-wizz-refs` refcount incremented and is reused rather than duplicated, so a component mounted in several places injects its stylesheet exactly once.
- `__wizzReleaseHead(nodes)` — removes the nodes (destroy cascade); scoped styles decrement `data-wizz-refs` and are removed only at zero.
- `__wizzClaimHead(nodes)` — hydration ownership: re-tags `data-wizz-head`, strips `data-wizz-head-id`, fronts claimed titles.
- `__wizzFindHeadRun()` / `__wizzStripHeadRun()` — locate and remove the dev server's marker-delivered head run.
- `__wizzStripOwnedHeadSlice(owner)` — remove one owner's unclaimed delivered nodes (nested fallback cleanup).

A styled component also emits a `createStyleNodes()` factory building its scoped `<style>` node (scope and location attributes set, CSS through the shared `scopeCss` pass). In the hydrate path the factory runs before `__wizzApplyHead`, so the fresh node acts as a probe: when adoption finds the server-delivered stylesheet by scope, the probe is discarded and the delivered copy is refcounted instead.

The initial `__wizzChanged` object is derived from reactive script declarations, for example `{ count: true, user: true }`. When no reactive declarations exist, it is emitted as `{  }`; `update()` remains safe because it has no dependency guards to satisfy.

## Current Runtime Boundaries

The generated output is intentionally small and uses direct DOM APIs. Its current behavior has a few boundaries that future work should address deliberately:

- Components must have at least one top-level element. Root-level formatting text is ignored, and additional top-level elements are not mounted because creation selects the first root element.
- Imported component tags accept attributes as props but no children and no event directives; components inside each blocks remain unsupported, so component identity semantics are defined for directly nested components only.
- Prop bindings are read-only at statement level; expression-position mutations of a prop name (`if (name = x)`, call arguments) pass through undetected, the same documented boundary the assignment interceptor has for reactive state.
- Dynamic expressions are supported as direct text-node children and as brace-valued attributes. `value`, `checked`, and `disabled` use property assignment; other dynamic attributes use HTML attributes through `__wizzAttr`. HTML boolean attributes toggle presence by truthiness, and any dynamic attribute is removed for `null`/`undefined`. Outside the boolean list `false` renders `"false"`, so an author who wants a non-boolean attribute gone must pass `null`.
- Explicit event directives use `on:<event>={handler}` and compile to native `addEventListener()` bindings. A handler may be a component-local identifier or any non-empty JavaScript listener expression, such as `(event) => increment(event.detail)`; reactive assignments inside inline handlers are intercepted like script mutations. Inline event attributes are not supported.
- The update function queries the document each time a dependency changes and assumes the target still exists. The current output has no null-target guard or caching layer.
- Repeated dependencies generate separate guards by expression dependency. Updates are batched per microtask with merged flags, but there is no granularity below a component: one changed dependency re-runs every guard that references it in a single pass.
- Lifecycle hook callbacks registered after mounting or destroy never fire.
- The emitted developer script must be valid JavaScript in the component factory context. The interceptor is syntax-aware but not a complete JavaScript parser or sandbox: mutations in expression position (call arguments, conditions, object literals, template interpolations), unbraced control-flow bodies, chained assignments beyond the first target, and destructuring pass through untransformed, and statements whose extent cannot be established confidently are never rewritten.
- `destroy()` runs destroy hooks, destroys child components, removes every tracked event listener, and removes the generated root from the provided target. Listeners that component code attaches itself (for example to `window` or `document` inside `onMount`) are not tracked; clean those up in `onDestroy`.
- Server output renders HTML strings with a fixed escaping boundary but makes no attempt to sanitize the author's own static markup — a `<script>` tag authored literally in a template is emitted verbatim. The server target executes the author's top-level script verbatim and trusted; treat `.wizz` sources as application code, not user input.
- Author scripts that read browser globals (for example `document.location.search`) pass the static-renderability gate but fail `renderComponent()` at runtime in Node. Delivering code (the dev server, `ssr-demo.js`) catches the failure and streams the plain shell — assigning browser-global reads to non-reactive `const`s is the author's responsibility, the same contract other frameworks use for module-level nondeterminism.
- Hydration verification is strict: CRLF-authored templates, post-render DOM mutation by extensions or scripts, and whitespace differences all fall back to a full client mount rather than partially adopting markup. The fallback is always safe; a partial adoption is never attempted.
- Hydration creates exactly one node: the `{#each}` list anchor (an empty text node cannot survive HTML serialization). Every other delivered node is adopted in place across if branches, list items, and nested components.
- Branch selection during hydration re-evaluates the same test the server evaluated against seeded state, so a nondeterministic author expression (`Date.now()`, `Math.random()`) can select a different branch in the browser; the walk then falls back cleanly.
- The delivered state script must remain a sibling of the mount point. Placing it inside the hydrated root breaks the child-count verification and forces the client fallback.
- Head management is mount/navigation-scoped, not reactive: `<title>{title}</title>` and `content={description}` evaluate at mount time client-side and at render time server-side, and subsequent state changes never rewrite head nodes. Head follows navigation, not state changes. Multiple `<title>` declarations across simultaneously mounted components warn once (development only) and resolve last-in-tree-wins by head position; `<meta>`/`<link>` concatenate.

## Tests

Each generator module has a focused Node test file. Run the complete generator suite from the repository root with:

```bash
node --test src/compiler/generator/*.test.js
```

The tests verify source formatting, safe reactive-assignment interception, DOM construction, preservation of escaped source text, missing-root errors, dependency-specific text updates, no-query static output, ES module export shape, reactive context getters, initial rendering, and `destroy()` behavior. Server-target tests execute generated modules and pin the rendered HTML, escaping, state serialization, and every surface rejection; hydration tests pin the adoption-walk emission and its runtime behavior against delivered markup. A byte-for-byte pin guards default `mountComponent` output against accidental hydration-path leakage. Update the nearest test whenever changing generated source or its runtime contract.

`../../test/benchmarks.test.js` adds deterministic benchmark regressions using representative fixtures. It verifies that 1,000 synchronous event-driven mutations schedule one update and perform one lookup/write, that 25 listener-heavy mount/destroy cycles remove every tracked listener, and that a 121-element static tree mounts without reactive lookups. The tests report durations for local comparison but assert operation counts rather than elapsed-time limits, keeping the suite reliable across machines and CI environments.
